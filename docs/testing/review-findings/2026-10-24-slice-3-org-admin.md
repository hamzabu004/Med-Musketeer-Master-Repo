# Code review findings — Slice 3 part 2 (organisation-admin API, ZITADEL accounts)

- **Reviewed:** uncommitted work on `feat/cloud-org-admin`, `/code-review`, 2026-10-24
- **Status:** Findings 1 to 3 fixed before merging (2026-10-24), as they break the access rules this slice enforces. Findings 4 to 9 are open, deferred to the testing phase.
- **Verified so far:** findings 1 and 2 (each regression test fails without its fix: the request does not wait for the concurrent change and succeeds); finding 3 (ZITADEL v4.20.0 answers a second deactivate with HTTP 400 "User already inactive"). The others are as reported.

|---|---|---|---|---|---|
| 1 | High — **Fixed 2026-10-24** | `cloud/backend/app/organisation.py` (`issue_wearable`) | The open `device_grants` row is read without a lock (`FOR SHARE OF d` locks only the device), so it races with the system admin's grant revoke. | Grant revoke commits between the issue's check and its insert: the wearable is assigned to a patient of an organisation that no longer holds the grant, and its data is filed under that patient. | `FOR SHARE OF d, g`. | 2 | High — **Fixed 2026-10-24** | `cloud/backend/app/accounts.py` (`disable_account`) with `organisation.py` (`issue_wearable`, `assign_doctor`) | Disable locks only the `users` row; issue locks the `patients` row, and the doctor check in assign has no lock. | A concurrent disable and issue/assign both commit: a disabled patient with an open wearable assignment, or a disabled doctor with an active patient. | Lock the `users` row (`FOR SHARE`) in issue and assign. Tests: `test_issuing_a_wearable_waits_for_a_concurrent_patient_disable`, `test_assigning_a_doctor_waits_for_a_concurrent_doctor_disable`. |
| 3 | High — **Fixed 2026-10-24** | `cloud/backend/app/accounts.py` (`disable_account`) | Only a 404 from ZITADEL's deactivate is tolerated; an already-inactive user is reported by ZITADEL as a precondition error (400 → 422). | Deactivate succeeded in ZITADEL but the response timed out, or the user was deactivated in the console: every retry answers 422 and `users.status` stays `active`, so the user keeps API access. | `ZitadelAdmin.deactivate_user` treats a 400 as done when ZITADEL reports the user as `USER_STATE_INACTIVE`. | 4 | Medium | `cloud/backend/app/accounts.py` (`create_account`), `registry.py` (`create_organisation`) | The ZITADEL undo runs only on `IntegrityError`. | An audit insert error, commit failure, other DB error, cancellation, or a timed-out create that ZITADEL did complete leaves a ZITADEL user with the e-mail as username: every retry gets 409. | Undo on any exception; on a timed-out create, look the user up by username before retrying. |
| 5 | Medium | `cloud/backend/app/accounts.py` (`create_account`) | The organisation row stays `FOR SHARE`-locked and the DB connection held across up to four sequential ZITADEL calls. | A slow ZITADEL blocks organisation suspension and can use up the connection pool for every endpoint. | Validate, release, call ZITADEL, then write in a short transaction. |
| 6 | Medium | `cloud/backend/app/zitadel_bootstrap.py` (`token_works`, `replace_personal_access_token`) | Any non-200 (5xx, 429) counts as an invalid token, and old tokens are deleted before the new one is created and written. | A ZITADEL hiccup during `compose up` deletes the API's working token; if minting or writing the new one then fails, account endpoints answer 502 until the job runs again. | Rotate only on 401/403; create and write the new token before deleting the old ones. |
| 7 | Low | `cloud/backend/migrations/versions/0002_accounts_and_audit.py` | The only index is `(scope, org_id, at)`; `GET /audit` filters on `org_id` alone and `GET /admin/audit` on `scope` ordered by `at`. | Both become full scans and sorts as the append-only log grows. | Indexes `(org_id, at)` and `(scope, at)`. |
| 8 | Low | `cloud/backend/app/accounts.py` (`disable_account`) | Disabling writes only `account.disabled`, not the wearable return or the ended care assignments; a disabled patient's care assignment stays open. | The audit log cannot show which wearable was returned or which assignments ended. | Write `wearable.returned` / `doctor.unassigned` events; decide whether a disabled patient's care assignment ends. |
| 9 | Low | `cloud/backend/app/zitadel_bootstrap.py` | `write_private` duplicates the atomic write still done inline for the config file. | The two copies drift. | One shared `write_atomic(path, content, mode)`. |
