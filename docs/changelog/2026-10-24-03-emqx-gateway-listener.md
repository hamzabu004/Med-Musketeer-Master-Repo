# EMQX gateway listener, broker hooks and the cloud certificate (Iteration 3, Slice 4)

- **Date:** 2026-10-24
- **Type:** code
- **Module:** M7 cloud, M1 CA tool
- **Commits:** see `git log -- cloud/ tools/ca-tool/`

## What changed
- **CA tool:** `mmca issue cloud [--replace]` issues the EMQX gateway listener's server certificate (CN/SAN `cloud.medmusketeer.local`, serverAuth, EC P-256) into `cloud/` of the data directory. Every certificate now carries key identifiers (SKI on the CA and leaves, AKI on leaves).
- **EMQX:** an image built from `cloud/emqx/` with the configuration baked in. Secrets (hook secret, Erlang cookie) are rendered into `etc/emqx.conf` at start, because EMQX 6 does not substitute environment variables there. The image defaults (plain 1883, demo-certificate 8883, WebSocket) are off. There are two listeners:
  - `ssl:gateway` on 8883: mTLS with the MedMusketeer CA, username = certificate CN;
  - `tcp:internal` on 1883: for the adapter (`mm-adapter`, password).
- **Hooks in the API** (`app/broker.py`, `/internal/emqx/...`, shared secret):
  - Gateway authentication requires the *presented certificate's* SHA-256 fingerprint to be an active, unexpired `x509_mtls` credential of an active `fixed_gateway`. This refines D4. For `x509_mtls`, `credential_ref` is now that fingerprint, and the registry API checks and normalises it.
  - Topic authorisation follows D5; the adapter may only read `ingest/#`.
  - Authentication decisions are logged with reason and check time; the API now configures its own logging with millisecond timestamps.
- **D1 implemented:** the rule republishes gateway messages to `ingest/{gateway}/{topic}` as JSON, with the broker receive time.
- **Install script:** `cloud/scripts/install-emqx-certs.sh` streams the certificate into the new `emqx-certs` volume through a `tools`-profile compose service. Without the certificate, the gateway listener stays off with a warning.
- **New settings:** `EMQX_HOOK_SECRET`, `EMQX_ADAPTER_PASSWORD`, `EMQX_NODE_COOKIE` (generated by `init-env.sh`, and appended to the existing dev `.env`), plus the ports `EMQX_GATEWAY_PUBLISHED_PORT`, `EMQX_INTERNAL_PUBLISHED_PORT` and `EMQX_GATEWAY_BIND_ADDRESS`.
- **Tests:** the compose-stack fixture is shared by all stack tests (one stack per session). It now creates a throwaway CA with the real CA tool and installs the cloud certificate before `up`. `paho-mqtt` is a test dependency.
- **Decisions:** D13 (EMQX configuration, internal listener); D1/D4/D5 marked implemented and verified on EMQX 6.3.2; `gaps.md`, `stack.md`, `ca-tool-spec.md` updated.

## Why
- Slice 4 of `docs/iterations/iteration-3-cloud.md`: gateways need an authenticated, ACL-limited way into the cloud before the uplink bridge (Iteration 4).
- The key identifiers were found while testing: Python 3.13+'s default TLS context refuses mmca chains without them ("Missing Authority Key Identifier").
- The CA on the custodian's machine predates the change and has no SKI. Chains from it still fail strict verification; replacing it is an open decision in `gaps.md`.

## Evidence
289 cloud tests pass (50 unit, the rest against a database container or the full stack), and 51 CA-tool tests (the Mosquitto interop tests, which need Podman, were not run). On the full stack:
- TC-C14: a registered gateway's alert reaches the adapter with the broker-attested username.
- TC-C15: a revoked certificate is refused at once on reconnect, while a new certificate for the same gateway works.
- TC-C16: foreign-CA and certificate-less clients are refused in the TLS handshake; wearable and unregistered certificates are refused by the API.
- TC-C17: every out-of-ACL publish and subscription gets "Not authorized", and the monitor sees none of them.
- TC-C18: the listener presents `cloud.medmusketeer.local`; a wrong pin or another CA is refused.

Records, EMQX and API logs are in `docs/testing/evidence/2026-10-24/cloud/stack/`.
